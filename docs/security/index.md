# Аудит безопасности

Дата: 2026-09-17. Область: весь код приложения (Swift), скрипты сборки,
транспорт. Метод: ручной разбор поверхности атаки + тесты на найденное.

## Модель угроз

Chelka — личный инструмент: обе машины принадлежат одному человеку и связаны
его tailnet. Рассматриваемые источники угроз:

| Источник | Рассматривается |
|---|---|
| Вредоносные файлы, брошенные на полку / прилетевшие с пира | да |
| Скомпрометированный пир (вторая машина) | да |
| Сетевой атакующий | частично — сеть закрывает Tailscale (WireGuard) |
| Вредоносное значение в настройках (`peerHost`) | да |
| Локальный атакующий с правами пользователя | нет — он и так может всё, что может приложение |

## Находки и их статус

### Ф1. Инъекция аргументов через `peerHost` — ИСПРАВЛЕНО

`peerHost` из UserDefaults попадал в аргументы `ssh`/`rsync` без проверки:
значение вида `-oProxyCommand=…` интерпретировалось бы как опция с
выполнением произвольной команды. Исправление: валидация
(`ChelkaCore.PeerHost.isValid` — только hostname/FQDN/IPv4, опционально
`user@`; опции, пробелы, `;`, backticks, `$()`, переводы строк отклоняются)
плюс `--`-разделитель перед хостом в вызове ssh. Покрыто 17 тестами.

### Ф2. Перезапись одноимённого файла на приёмнике — ИСПРАВЛЕНО

`rsync -a` молча перезаписывал на пире файл с тем же именем (потеря данных:
на обеих полках лежит свой `report.pdf` → push стирает чужой). Исправление:
`--ignore-existing` — существующий файл на приёмнике никогда не трогается.

### Ф3. Локальная инъекция в командную строку — НЕ ОБНАРУЖЕНО

Все внешние процессы запускаются через `Process` с массивом аргументов,
shell не участвует. Имена файлов в аргументы опций попасть не могут:
источник rsync — всегда абсолютный путь (`/Users/…`), начинаться с `-`
не может. Имя файла передаётся протоколом rsync, а не удалённым shell.

### Ф4. SSH-ключ транспорта даёт полный shell на пире — ИСПРАВЛЕНО

Транспортный ключ зажимается forced command: в `authorized_keys` приёмника
строка ключа получает префикс `restrict,command="~/.chelka-receive"`
(обёртка — `scripts/chelka-receive.sh`, шаг установки в README). После этого
ключ может только: `mkdir -p Shelf` и приём rsync в `Shelf/`. Shell, любые
другие команды, чтение файлов (`--sender`), запись мимо `Shelf/` и
shell-метасимволы отклоняются. Обёртка покрыта 10 тестами (`make test`).
Проверено вживую: `ssh <peer> id` по транспортному ключу — отказ.

### Ф5. TOFU при первом подключении — ИСПРАВЛЕНО

Транспорт использует `StrictHostKeyChecking=yes`: host key должен быть уже
запиннен в `known_hosts`, любая подмена узла — жёсткий отказ. Пиннинг
происходит один раз интерактивно на шаге `ssh-copy-id` (человек видит
fingerprint), приложение слепо ключи не принимает.

### Ф6. Файлы с пира приходят без quarantine — ИСПРАВЛЕНО

rsync не ставит com.apple.quarantine, поэтому приёмник делает это сам:
watcher помечает карантином каждый файл, появившийся на полке не через
локальный дроп (`Quarantine.markIfNeeded` + `Sync.newcomers`). Список
виденных имён переживает перезапуск, так что файлы, прилетевшие пока
приложение не работало, помечаются при следующем запуске. Исполняемое из
полки теперь проходит Gatekeeper как любая загрузка. Проверено вживую на
обеих машинах (xattr com.apple.quarantine присутствует).

### Ф7. Прочее проверенное

- **Path traversal в имени принимаемого файла**: rsync отбрасывает ведущие
  `/` и `..` — запись возможна только в `Shelf/`.
- **Превью вредоносных файлов**: генерирует системный сервис QuickLook в
  своей песочнице, не приложение.
- **Symlink на полке**: копируется как symlink, содержимое цели не уезжает.
- **Удаление**: только в Корзину (`trashItem`), необратимого удаления в
  приложении нет.
- **Секреты**: приложение не хранит и не логирует ключи/пароли; в unified log
  попадают только имена файлов и коды ошибок (минимальная утечка метаданных —
  лог локальный).
- **Sandbox выключен** — необходим для запуска ssh/rsync; подпись ad-hoc.
  Пользователь собирает приложение из исходников сам (`make install`),
  цепочка доверия — git-репозиторий.

## Тесты безопасности

`make test` (Sources/chelka-selftest): 66 проверок, из них по безопасности:
17 — валидация `peerHost` (инъекция опций, shell-метасимволы, переводы строк,
длина, двойной `@`); 10 — обёртка `chelka-receive.sh` (shell/команды/чтение/
запись мимо Shelf/ отклоняются, законный приём проходит); 4 — логика
карантина новоприбывших. Остальные — имена файлов, геометрия, превью.

## Рекомендации пользователю

1. Приватный ключ `~/.ssh/id_chelka` — только на машине-отправителе, права 600.
2. В tailnet ACL ограничьте доступ к порту 22 только своими устройствами.
3. Не указывайте в `peerHost` машины, которым не доверяете как своим.
4. Обновляйте приложение из исходников (`git pull && make install`).
